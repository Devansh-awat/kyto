  - **The 504s are HackClub's own 5-second header timeout.** `UPSTREAM_HEADER_TIMEOUT_MS = 5_000` in hackclub/ai `src/routes/proxy/v1/general.ts` (`fetchWithHeaderTimeout`, added 2026-05-24 in PR #110) aborts any upstream request that has not returned response **headers** within 5s and throws `HTTPException(504, 'Upstream did not return response headers within 5000ms')`. Something in front of the app (the README mandates a reverse proxy) swaps that body for a Hack Club branded HTML error page, which is why the real message never reaches us and why it looked like a CDN fault. The app's own `onError` returns JSON, never HTML — so an HTML body from this proxy always means the edge, not the app.

- **A CUT-OFF STREAM is not a model failure, and must not cost a fallback rung** (`truncatedStream` in `agent/index.ts`, 2026-08-22). Zen sometimes closes the SSE connection with **no `finish_reason` and no `[DONE]`** — reproduced from the container: a long reply or a long reasoning block gets cut at ~100-220KB of stream, ~35-45s in, on roughly a third of long turns, with the last chunk simply missing. The openai-compatible mapper leaves its default `other` in place for that (its `switch` maps only stop/length/tool_calls/content_filter), so `other` **is** the tell: no healthy completion produces it. Two responses, by what had already happened:
  - **Text had streamed** → the same continuation path a `length` finish uses (`continueTruncatedReply`, tools off, same model, up to `MAX_CONTINUATIONS`), and a continuation that is ITSELF cut off (`other`) gets another round. The user reads one whole reply instead of a dangling half-sentence.
  - **Nothing had streamed and no tool ran** → **re-run the SAME attempt in place**, up to `MAX_TRUNCATION_RETRIES` (2), logged as `[agent] stream was cut off before the model said anything; retrying the same model`. Safe precisely because nothing ran: no text was shown, no tool fired, so there is no side effect to repeat. `modelTaskId` carries the retry counter (a retry does not push onto `attempts`, so a shared id would re-open a completed card).
  - An attempt that DID run tools keeps the old path — `synthesizeFinalAnswer` already had a go, and re-running the whole attempt could fire a side effect twice.

- **A model that starts LOOPING is not "handled"** (`lib/agent/degenerate.ts`, `DegenerateOutputError`). Weak models fall into token loops and emit the same line forever — formally reply text, so the old loop posted it and counted the turn as answered. `createRepetitionGuard` watches the streamed text and trips on **8 consecutive identical lines** (outside a code fence — a data dump legitimately repeats) or a **runaway single line** (24+ whitespace tokens with ≤2 distinct ones). On a trip: the offending chunk is never yielded, `reply.drop()` purges the unposted buffer (the guard fires ~70 chars in, well under the 280-char post threshold, so nothing reaches Slack), the attempt aborts, and `stripRepeatedLines` scrubs the loop out of the continuation context before the next model sees it. With `StreamInterruptedError`, one of the only two errors allowed to fall back after text has already streamed.
- **An ATTEMPT is "handled" iff IT produced reply text or a deliberate `skip`** — tracked per attempt, not per turn. A continuation attempt (below) inherits the turn's already-streamed text, and a turn-level flag would let it claim success having written nothing.
- **A provider that dies MID-STREAM does not throw** (`StreamInterruptedError`, `lib/errors.ts`). A step whose request fails after the SDK's internal retries becomes an `error` part on `fullStream` and the stream just ends. With text already streamed the turn looked handled, so kyto went **silent mid-task** while the journal logged `turn complete` — the real "stops in the middle" bug (observed: a provider 429 nine tool-steps into a long monitoring turn). Now an `error` part whose attempt never finished on `stop` raises, and this is the **one** case where a turn that already streamed text may still fall back: the next model is prompted with `renderContinuation` (the tail of what the user was already shown — "do not repeat it, continue") plus the usual `renderCarryover`.
- **"Stops in the middle" / ends a turn without responding**: a model that ran tools then ended with **no text** left the user staring at tool cards. It now runs `synthesizeFinalAnswer` — re-ask **the same model, once, with `tools: {}`**, feeding it the task plus `renderCarryover(gatheredResults)` and "you already did the work, write the final reply now". Tools are off, so nothing can fire twice, and it costs one cheap call. It fires on **any** finish reason: the turns that actually went silent ended on `length` (cut off mid-tool-call by `MAX_OUTPUT_TOKENS`) or `tool-calls` (`MAX_STEPS` hit with a call pending) — exactly what the old clean-`stop`-only guard excluded. If the nudge is empty too, the turn is unhandled and falls back. Provider placeholder text (`(Empty response: ...)`) is dropped before it reaches Slack.
- **Truncated tool-call JSON is repaired, not fatal** (`repairTruncatedToolCall`, wired as `experimental_repairToolCall`). A model writing a large file or a long message can hit `maxOutputTokens` **mid-argument**, leaving unterminated JSON — the SDK's default is an unrecoverable `AI_InvalidToolInputError: AI_JSONParseError` that stranded the turn. `closeTruncatedJson` walks the fragment tracking string/escape state and the bracket stack, drops a trailing escape or separator, and appends the owed closers; if the result parses, the call runs with the content that DID arrive and the model continues (e.g. with `writeFile append`). Unclosable → null, and the SDK's normal error path takes over.
- **Tool-result carryover across fallback**: `renderStream`'s `onToolResult` reports every completed tool call's input+output; the agent stashes them in `gatheredResults` (deduped by tool+input). On a fallback attempt the prompt is augmented with `renderCarryover` — "a previous attempt already ran these tools, answer from them, do NOT re-run" — so the new model continues instead of repeating identical web searches. Bounded (last 12, each clamped). A prompt-level replay, not session continuation.
- **One fallback, not two.** A dead HackClub used to cost several `Thinking · fallback` cards and minutes of latency. Three fixes: **`maxRetries: 1`** on `streamAttempt` (the SDK's default of 3 internal tries just tripled the wait before our own cross-provider fallback could run); **`deepErrorText`** (`lib/utils/error.ts`), which recurses through `lastError`/`cause`/`errors` because the budget 403 (`Key limit exceeded (daily limit)`) hangs off *wrapped* errors' `responseBody`, not the `AI_RetryError` message, and so was invisible; and **`HACKCLUB_OUTAGE_THRESHOLD = 1`**, since every HackClub rung shares one proxy and one budget — a rung failing for a non-model reason means the next fails identically.
- **A GATEWAY failure is replayed, not routed away from** (`packages/ai/src/gateway-retry.ts`, wired into both per-attempt fetches in `agent.ts`). HackClub's edge answers a burst of requests with a Cloudflare **504** — measured 2026-07-27 at ~1 in 6 for several minutes, always ~5.4s in, the same rate for a 300-byte and a 70KB body, reproducible with bare `curl` and no kyto in the path (journal: 21 such 504s on 07-25, 6 on 07-26, 29 on 07-27). A turn issues one request per agentic step, so at that rate a long turn nearly always lost a step, and the loop — which cannot tell "the proxy dropped one request" from "this model died" — abandoned a healthy primary mid-task. So a response carrying a gateway status (408/502/503/504/520/522/524) is now sent again, up to 2 retries at 300ms/1200ms, before the SDK ever sees it: ~17% per-step death becomes ~0.5%, while a proxy that is genuinely down still costs at most ~16s before the fallback runs. Safe **only** for these statuses — the status came from the proxy, so nothing was generated, nothing billed, no completion byte streamed. Everything else (any 4xx, a 429/budget, a stream that dies after it started) is untouched and still routes away on the FIRST failure, which is why `maxRetries` stays 1. Exhausting the retries returns the failure unchanged, so the walk below is reached exactly as before; each replay logs `[agent] gateway failure, retrying the same request`.
- **What made those 504s visible on 2026-07-27 was OUR change, not theirs**: `HACKCLUB_OUTAGE_THRESHOLD = 1` means one proxy-reported failure writes off all 19 HackClub rungs for the turn. Until the DigitalOcean tier was deleted that morning, that write-off landed on kimi-k2.6 and the walk stayed decent; afterwards a single transient 504 dropped the turn from the pinned primary straight to `gemini-3.1-flash-lite`. The retry above is the first line of defence; whether a gateway status should count toward the outage threshold **at all** is still open (a spend 429 condemns the tier, an edge timeout arguably says nothing about opus-4.8).
- **HackClub outage → skip the rest of HackClub**: a per-turn `hackclubFailures` counter trips `hackclubUnavailable`, making attempt selection skip all remaining HackClub rungs and jump to Gemini. What counts is decided by `condemnsHackclub(status)` (`lib/agent/routing.ts`): a proxy-reported status that is NOT a gateway status. A fault kyto raised itself (empty response, degenerate loop) has no status and says nothing about the proxy; a 504 that survived the retries above is a lost request, not a dead tier. A full outage still reaches a working model in ~2 attempts.
- **HackClub spend-limit → straight past HackClub**: a daily-spend 429 sets `hackclubBudgetExhausted` (the budget is shared, so every other HackClub rung would 429 identically) and every remaining HackClub rung is skipped at selection time, leaving Gemini. The write-off is applied when the next attempt is **selected**, not baked into the queue, since a tier can go out mid-walk.
- **`max_tokens` capping** (`MAX_OUTPUT_TOKENS = 8000`, applied as `maxOutputTokens` on HackClub and BYOK attempts): the HackClub proxy enforces its daily spend limit **pessimistically** — with no `max_tokens` it assumes the model could emit its full max output and 429s on that projection **even with budget free**. Injecting it makes the proxy price off the bound. Sized to observed usage (step outputs run <6k tokens). Raise it if large single-step writes get truncated — though a truncated tool call is now repaired rather than fatal (above).
- **Prompt caching** (`addCacheControl`): `tuneBody` injects `cache_control` breakpoints on the **FIRST system message** (the static prompt every thread shares), the **last replayed history message** (`historyMessages`), and the **last message of any role** (so the breakpoint advances over the growing tool tail each step). OpenRouter translates `cache_control` to OpenAI's explicit breakpoint (verified 2026-10-08). The `ttl: '1h'` is ignored by luna — its cache lives 30 min.
  - **Why the history is one message per Slack message (2026-10-08).** gpt-6-luna (OpenAI's newer models) looks a cache up ONLY at message endings and explicit breakpoints, never at an arbitrary prefix, and every uncached token is billed as a cache WRITE at 1.25x ($0.125/M vs $0.01/M read). With history + tail in one user message, the only boundary two turns shared was the end of the system prompt: production read exactly 15,507 tokens on every turn of a thread whatever its length, and single-step turns hit 24% (half read 0). Measured through the proxy: history in its own message WITHOUT a breakpoint still missed; with one, turn 2 read 87–91%, ~3–6x cheaper. Overall luna hit rate before the fix: 76% by tokens, misses ~68% of the input bill.
  - **Tools changes break everything after them** (OpenAI docs: names, descriptions, schemas, order). So the `loadTools` catalog lists EVERY deferred tool (it used to drop loaded ones, changing on every load), Jev's preload is remembered for the thread, and the order persists per thread (`threadToolOrder` in `loaded-tools.ts`, fed to `stabilizeToolOrder`). Turns whose preload differed read 0.
  - **What stays uncached by design**: the tail — the thinking block (p50 ~3k, p90 ~12k tokens; rewritten each turn), the clock, the new message — and after each step only the newest tool output. A different SPEAKER in a thread changes the memory list (context half) and possibly the toolset; that turn re-reads from the static prompt.
  - **NOTHING VOLATILE MAY ENTER THE SYSTEM PROMPT.** It is sent as one string, so one changed byte invalidates the whole system+tools prefix — the single biggest cached block. The current time (to the millisecond) and the id of the message being answered lived in `contextPrompt` until 2026-08-05, which meant that prefix could never hit across a thread's turns; both now sit in the volatile tail of the user message (`buildPrompt`, below the replayed history). Keep `contextPrompt` to facts stable for the life of a thread.
  - **Tool schemas are part of that prefix too**, and they are serialized ahead of the messages: a `loadTools` call that grows the array mid-turn invalidates everything after it for the rest of that turn. That is why a thread's loaded set now survives the turn (`lib/ai/loaded-tools.ts`).
  - **`cache-probe.ts` measures it.** Each request is split into the units a provider serializes in order (tools, then each message) and compared with the previous step's; anything that is not a pure APPEND logs `[agent] prompt prefix changed mid-turn; cache lost from here` with the unit that diverged and the share of the request that could still be cached. Read it with `journalctl -u kyto.service | grep 'prompt prefix changed'`.
- **The subagent and compaction are SPLIT** (2026-08-21, owner's ask "subagent use same deepseek v4 flash"). `subagentAttempts` = `PRIMARY_ATTEMPT` itself (it has followed the primary onto Ox Alpha, then GLM 5.3 Flash, briefly TokenBom, and back to GLM 5.3 Flash, and follows whatever comes next) then Gemini: a subagent is doing a slice of the turn's own work and reporting back into it, so a different model class meant the delegated half came back in a different voice and worse at tool calling than the parent. `compactionAttempts` = Gemini then the FORMER HackClub primary (`deepseek-v4-flash-0731`, NOT the current primary), deliberately UNCHANGED otherwise: one compaction pass digests up to 200 messages, a long-idle thread catches up over many passes, and it runs in the BACKGROUND where nobody sees the bill. Do not collapse the two lists back together.
- **Gemini tool use needs `thought_signature` replay**: Gemini 3.x attaches an encrypted `thought_signature` to every function call and REQUIRES it echoed back, or Google 400s. The openai-compatible provider drops it when replaying assistant tool calls, which broke ALL multi-step Gemini tool turns. `tunedFetch` tees each response, captures `extra_content.google.thought_signature` per tool-call id, and re-injects them into subsequent request bodies. A dummy signature is rejected, so real capture is mandatory.
- **The ChatGPT (Codex) attempt must tell the SDK `store: false`, not just force it on the wire.** `streamAttempt` passes `providerOptions.openai = { store: false, reasoningSummary: 'auto' }` for `CHATGPT_PROVIDER`; `codexFetch` still pins `store:false` in the body as a backstop. Knowing store is off is what makes `@ai-sdk/openai` add `include: ['reasoning.encrypted_content']` and replay reasoning items **with their payload** instead of by `rs_…` id. While only the fetch-level force was in place, every multi-step ChatGPT tool turn died on its SECOND step with `404 Item with id 'rs_…' not found. Items are not persisted when 'store' is set to false` — the reason a linked account fell back to the shared models constantly while the same account is fine in Codex itself. `reasoningSummary: 'auto'` is the other half of mirroring Codex: it's what puts thinking in the plan card. The attempt also carries Codex's client headers (`originator: codex_cli_rs`, `version` = `CODEX_CLIENT_VERSION`, per-attempt `session_id`).
- **Per-attempt watchdog** (`ATTEMPT_TIMEOUT_MS`, default 10m, env `AGENT_ATTEMPT_TIMEOUT_MS`): each attempt runs under its own `AbortController` combined with the turn controller via `AbortSignal.any`. If an attempt stalls (frozen SSE, hung tool) the timer aborts **only the attempt signal**, so it is NOT mistaken for a user interrupt and routes through the normal recovery path. The combined signal also reaches tool execution. It is **re-armable**: the `wait` tool calls `extendAttemptDeadline` so a deliberate pause (up to an hour) doesn't read as a stall.
- **Budget-exhausted message**: when a turn dies after the spend-limit cascaded through every fallback, `agent/index.ts` throws `BudgetExhaustedError` and `agentErrorMessage` (`lib/errors.ts`) names the cap and the reset countdown ("kyto's daily model budget ($3/day) is used up … it resets at UK midnight, in Xh Ym"). `timeUntilUkReset` counts to the next Europe/London midnight (tracks BST/GMT, host-tz independent).
- **Parallel tool calls**: the model may emit several tool calls in one step and the SDK runs the batch concurrently. The only lever is behavioral, so the core prompt tells it to batch **read-only** lookups (file reads, Slack/web searches, URL fetches, list/get calls) into one step, and to issue **side-effecting** tools (send/edit message, deploy/remove site, canvas write, create channel, pin, email) **one at a time**. Batching is model-dependent; faster batched reads also keep a turn under Slack's interaction timeout.
- **A model whose deployment PINS a sampling parameter needs it sent** (`REQUIRED_TOP_P`, `packages/ai/src/agent.ts`): some deployments 400 unless an exact value is on the wire (`top_p must be 0.95 for this model`) and treat OMITTING it as wrong, which is what the SDK does by default — so such a rung is dead from the day it is added, visible only as a 400 partway down a walk. Keyed by model slug, **empty today** (the DigitalOcean roster that needed it is gone); kept because the failure mode is invisible without it.
- `glm-4.7` is omitted from HackClub (persistent 504); `glm-5.2` 504s intermittently but degrades via the empty-completion fallback.

- **The model can escalate ITSELF** (`upgradeModel`, `lib/ai/tools/upgrade-model.ts`, `UPGRADE_ATTEMPTS` in attempts.ts) — owner's call, 2026-08-05 ("model self escalate whenever needed … anyone can escalate it"). Calling it ENDS the attempt (a `stopWhen` condition, exactly like `skip`, so the weaker model can't carry on after asking to be replaced) and the turn continues on `moonshotai/kimi-k3`, then `anthropic/claude-sonnet-5`. The escalation is recorded in `attempts`, which is what makes the next attempt a FALLBACK and so replays `renderCarryover` + `renderContinuation` — the stronger model picks the work up, it doesn't restart it.
  - **Bounded twice, because the rungs are dear.** kimi-k3 is $3/M in and $15/M out against the primary's $0.14/$0.28, on the same $3/day shared cap: one long escalated turn could eat most of a day. So it is ONCE per turn and **8 per UTC day workspace-wide**; past either, the tool answers "carry on yourself" instead of failing the turn. Neither bound judges whether the task deserved it — they exist so a bad judgement, or an injection asking for one, costs a bounded amount.
  - **Tune it from the log, don't guess**: every call logs `[agent] model upgrade requested` (reason, user, thread, count today) and every accepted one `[agent] upgrading the turn to a stronger model`. Too many → tighten the wording in `corePrompt`; none at all → loosen it. That is the whole point of the counter.
  - It is CORE, not deferred: a model deciding "this is beyond me" cannot first be asked to spend a round trip loading the tool that says so.

## Turn logging

Every failure mode above is readable from the container's logs (`docker logs`, Coolify; `kyto.service` is masked) and, per thread, from `thread_logs`. Lifecycle lines in order: `[agent] turn started` → `routed turn` → `attempt started` → `[stream] attempt stream ended` (the `StreamTally`: textChars, toolCalls, finishReasons, errors) → `attempt handled the turn` / `attempt failed, falling back` → `turn complete` / `turn failed` (durationMs + `failedAttempts` = the whole walk). `streamAttempt`'s `onError` must stay — without it the SDK dumps a raw unattributed stack. `errorStatus()`/`deepErrorText()` dig the status/body out of the wrapped `AI_RetryError`/`APICallError` chain.

**Where the time went** (owner's ask 2026-10-05, read by kevinton): each attempt's `timing` (`stream/timing.ts`, tested) — `ttftMs`, `firstOutputMs` per step, `modelMs` vs `toolMs` (parallel calls once), `outputTokensPerSecond` (a step's first model output to its LAST, so tool time inside a step doesn't count against the model), the 8 slowest `tools` (an unfinished one marked). The turn's last line (`turn complete`/`interrupted`/`failed`) sums them as `timing` with `setupMs` (before the first attempt), `modelCalls`, and `ttftMs` — the time to first token of EVERY model request in the turn (each step of each attempt, plus synthesis nudges and continuations), in order. E2B: `[sandbox] materialized` splits `reconnectMs`/`createMs`/`bootstrapMs`; `[sandbox] paused` its `ms`. `threadLogText` picks these lines out before truncation; kevinton gets them only when it asks (`threadLogs` with `timing: true`), so a review with no slow turn doesn't pay for them.

## Fallback cache (2026-09-29)

`lib/agent/fallback-cache.ts` (tested) remembers, in memory for 30 minutes, the
failures that will repeat next turn: a rung that returned 401/402/403/404, and
the Hack Club TIER once its spend limit is hit. `renderTurn` seeds `failedKeys`
and `hackclubBudgetExhausted` from it before routing, so a spent cap no longer
costs every new message a doomed primary request and a `· fallback` card. The
turn log's `[agent] routed turn` carries `cachedDead` when anything was skipped.

- A person's own attempts are never cached (their key, their problem;

- No probe (owner's call): expiry is the only way back. A restart clears it.
