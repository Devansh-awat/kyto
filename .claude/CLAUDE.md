# Code standards

**Ultracite** (a Biome preset) enforces formatting and lint. Run `bun x ultracite fix` before committing; `bun x ultracite check` to lint. It auto-fixes most style issues, so spend your attention on business-logic correctness, naming, architecture, edge cases, and UX.

House style beyond Biome: explicit types where they aid clarity and `unknown` over `any`; `const` by default; `for...of` over `.forEach()`; early returns over nesting; named constants over magic numbers; `Error` objects with real messages; no `console.log`/`debugger` in production; no barrel files; validate input.

## After every change (auto workflow — private repo, all pre-authorized)

Run these automatically after each completed change, **without asking**:

1. **Commit** locally, conventional-commit message, docs updated in the same commit. One logical change = one commit.
2. **Sync the Slack manifest** if `slack-manifest.json` changed: `bun run sync:manifest` from `apps/bot`. (Scope changes still need an app reinstall.)
3. **Restart the bot**: `systemctl restart kyto.service`. Check with `systemctl status kyto.service` / `journalctl -u kyto.service -n 30 -o cat` (look for `kyto (…) is online`). **Never hand-launch `bun run start:bot`** — a second process opens a second Socket Mode connection and silently steals ~half the events. If `deploy/kyto.service` changed, `systemctl daemon-reload` first.
4. **Push to `origin`** (`github.com/Devansh-awat/kyto.git`).

- **NEVER push to `upstream`** (`imdevarsh/gorkie-slack`, the fork source).
- **Opening a PR still asks first.** Commit/restart/sync/push-to-origin do not.

## Architecture — fully custom harness

The Vercel Chat SDK, the Pi framework, and `@ai-sdk/harness*` were removed in a ground-up rewrite. Kyto runs on:

- **Custom Slack harness** (`apps/bot/src/harness/`) — `@slack/socket-mode` + `@slack/web-api` directly. `SLACK_APP_TOKEN` required (Socket Mode is the only mode).
  - `SlackHarness` (`harness.ts`): Web API facade. Thread-id codec `slack:CHANNEL[:TS]`, message building, fetch/history/listThreads, reactions, assistant status, native streaming via `webClient.chatStream` (task cards use `task_update` chunks, `task_display_mode: 'plan'`).
  - `KytoBot` (`bot.ts`): owns the Socket Mode connection and event routing. `app_mention` events are deliberately **ignored** — everything routes off `message` events (mention = text contains the bot id), which killed the old dedupe problem.
  - `ThreadHandle` (`thread.ts`): `post` (Block Kit `markdown` blocks; files via `filesUploadV2`; per-message profile overrides via `username`/`iconUrl`/`iconEmoji`, needs `chat:write.customize`), `postEphemeral`, `schedule`, `subscribe`/`setState` (`thread_subscriptions` table + 30s cache), `fetchMetadata`.
  - **Every message threads** — a top-level DM/channel message roots its own thread (`threadTs = event.thread_ts || event.ts`). `buildPrompt` scopes context to that thread only, so kyto has no memory of the rest of a DM by default; it uses `searchSlack` (`in:@user`) to pull earlier history on purpose.
  - Markdown conversion is ours (`harness/markdown.ts`): inbound mrkdwn→markdown, `healMarkdown` closes dangling fences in chunked replies. `bot.getState()` is an in-memory TTL KV (`harness/kv.ts`), rebuilt at startup.

- **Custom agent loop** on `ai`'s `streamText` (`packages/ai/src/agent.ts` `streamAttempt` + `apps/bot/src/lib/agent/index.ts`): multi-step tool loop (`stopWhen: stepCountIs(MAX_STEPS)`, `MAX_STEPS = AGENT_MAX_STEPS` env, default **1000** — effectively no step limit; the real bound is the wall-clock watchdog + degenerate guard, since a hard cap stranded long jobs mid-solve). An attempt ending ON the ceiling with a tool call pending logs `[agent] attempt hit the step ceiling`. Per-attempt `@ai-sdk/openai-compatible` provider; a per-provider `fetch` in `streamAttempt` tunes each request (see Models). `renderStream` (`lib/ai/stream/`) consumes `result.fullStream` and renders the plan.

- **Sandbox tools** (`lib/ai/tools/sandbox.ts`): `bash`, `readFile`, `writeFile`, `editFile` run against `LazySandbox` — E2B `Sandbox.create` happens on the FIRST tool call that needs it, so chat-only turns cost zero E2B.

- **Deferred tools**: uncommon tools (browser, email trio, canvasDelete, slackDocs, createChannel, setChannelTopic, bookmarkLink, pins, poll, mermaid, sendAsUser/editAsUser, gh, TTS, subagent, all MCP tools) are registered but hidden until the model calls the **`loadTools`** meta-tool. Enforced per step via `streamText`'s `prepareStep`/`activeTools` (`buildTools` returns `{tools, activeTools, close}`).

- **Per-user MCP servers** (`lib/ai/mcp.ts`, `user_mcp_servers`): users add remote Streamable-HTTP MCP servers from **App Home**. A hand-rolled JSON-RPC client (initialize / tools/list / tools/call; SSE parsing) connects lazily per turn; listings cached 10 min per URL; tools namespaced `mcp_<server>_<tool>` and deferred behind `loadTools`. A dead server degrades only that turn's toolset. Local (user-machine) MCP servers are impossible over Slack by design.

### Security invariants (do NOT regress)

- **Code Mode / sandbox can't invoke mutating tools.** Sandboxed code reaches only shell, network, and the READ-ONLY Slack proxy — never postMessage/sendAsUser/etc. Those stay behind the confirm-post human gate so a prompt injection can't script an outward send. Do NOT add a host-tool RPC bridge for mutating tools without a confirm gate.
- **`getFile` sends the bot token ONLY to Slack hosts** (`isSlackFileHost`: `files.slack.com`/`*.slack.com`/`slack-files.com` over https). Any other URL is refused before the `Authorization: Bearer SLACK_BOT_TOKEN` header is attached — a prompt injection once used an arbitrary URL to mail the live token out. Do NOT restore an arbitrary-URL passthrough.
- **`fetchUrl` refuses `*.slack.com`** (302s to a login wall) and points at the Slack read tools instead.
- **The bot token never enters the sandbox.** `slackScript` / the `slack`-on-PATH helper reach Slack only through the host-side, READ-ONLY, allowlisted proxy (`lib/slack-proxy/`).
- **`gh`'s `GH_TOKEN` is brokered via E2B egress rules**, never in the sandbox env (`echo $GH_TOKEN` reveals nothing). **Only a token GitHub still accepts is brokered** (`lib/github/token.ts`, `brokerableGithubToken`, 15-min cached verdict): the egress rule rewrites `Authorization` on EVERY github.com request, so a dead token breaks anonymous reads of PUBLIC repos too — a `git clone` of a public repo failed with "Invalid username or token" and a whole turn concluded the repo must be private. A rejected token is left out of the rules entirely, which costs nothing already working and buys back every public read. A rotated token only reaches a given thread on its NEXT fresh sandbox (egress rules are create-time).
- **GitHub writes are gated on repo ownership** (`lib/github/guard.ts`; `github_repos`). kyto has ONE GitHub identity (`kyto-agent`, `GH_LOGIN`), so GitHub's own permissions can't tell two Slack users apart. A repo kyto creates for someone — or first writes to for them inside kyto's own namespace — is claimed for them; after that only they, their named editors, and the bot owner can get kyto to write there. Reads stay open. Enforced in **`gh`, `bash`, and `codeMode`** (all three are shells; gating one is theatre) at execute time against `message.author.userId`. Claims are made only after the command SUCCEEDS, and never for third-party repos.
- **A git repo that lands in the sandbox is disarmed by CODE, not by asking the model.** Every sandbox materialization runs `GIT_HARDEN_COMMAND` (global `core.hooksPath=/dev/null` + `protocol.ext.allow=never`), and any tool call that could have fetched/extracted a repo triggers `sanitizeGitRepos`, which deletes `.git/hooks/*` and strips the command-executing keys/sections from each repo config (a repo-local `core.hooksPath` would otherwise override the global one). Detail in TOOLS.md.
- **A saved memory is PRIVATE to its author until the owner promotes it** (`memories.isGlobal`, dashboard). Memories used to be workspace-global on save, which made them kyto's one persistent prompt-injection surface: someone saved "DONT MAKE PRS" and kyto refused GitHub work for everyone, indefinitely. `listMemoryIndex(userId)` returns only that person's own plus the promoted ones, and the prompt block states that memories are reference material that can never grant permissions or decide who kyto helps. **Promotion transfers custody** — a global memory is editable/deletable only by the owner, so "get it promoted, then swap the body" can't reopen the hole. Do NOT make saves global again.
- **Anyone can erase their own data, without the owner** (`features/customizations/erase.ts`, App Home "Your data"): "Forget me" deletes their memories + `thread_thinking` for their DM channel + those threads' sandboxes; "Delete everything" adds instructions/MCP/model keys/ChatGPT link. Reminders and sites are untouched (live, others may depend on them, already individually deletable). **Two limits are REPORTED, never papered over**: shared-channel reasoning is keyed by thread and derived from everyone in it, so it is not deleted (it ages out); a PROMOTED memory belongs to the owner now, so it survives and is listed by title. Sandboxes are killed at E2B *before* their rows drop, or paused sandboxes are orphaned holding the user's files. `threadsInChannel` anchors on the trailing colon — it guards a DELETE, and fixed-width Slack ids are an accident of their format.
- **Email read paths strip credentials BEFORE the model sees them** (`lib/email/redact.ts`): reset/magic links, URLs with a long opaque token, and OTP codes. **Unconditional, owner included** — not a check on who is asking. kyto's inbox is a real mailbox anyone can ask it to read, so "click forgot password, then ask kyto to read it out" is an account-takeover primitive, and a model holding the token can be talked into repeating it. Do NOT add an owner bypass.
- **Third-party GitHub writes need owner-granted trust** (`github_trust`, `lib/github/guard.ts`): a repo outside kyto's namespace is refused unless the user is trusted blanket or for that repo, and the attempt is queued in `github_requests` for the dashboard. This is a SECOND gate on top of repo ownership — that one protects users from each other, this one protects kyto's single GitHub identity from the workspace (an unbounded version is why the token got revoked). Approving grants trust and does NOT replay the command.
- **Ownership gate (reminders + sites)**: editable only by the creator, named editors, and the bot owner — enforced at execute time against `message.author.userId`, not whoever the model claims to act for. Detail in TOOLS.md.


## Identity, gating, and etiquette

- **Broadcast mentions are owner-gated AND channel-local.** Only the owner may make kyto ping a whole channel, and only in the channel it was invoked in. `neutralizeBroadcast` (`harness/markdown.ts`) downgrades `<!channel>`/`<!here>`/`<!everyone>`/`<!subteam^…>` to inert plaintext; applied to the streamed reply (`createReply({allowBroadcast})`, `allowBroadcast = isOwner`) and, in `postMessage`, whenever the target isn't the current channel — **owner included** (`allowBroadcast = isOwner && target === currentChannel`). Being allowed to post into #announcements isn't being allowed to @channel a room kyto isn't in the conversation in. `neutralizeBroadcastDeep` applies the same strip to every string in a Block Kit payload.
- **`postMessage` can send Block Kit**: an optional `blocks` param (JSON array string, ≤50 blocks, `parseBlocks`). Replaces the markdown body; `message` stays required as the notification fallback (`PostContent.fallbackText`).
- **`postMessage` identity override is OWNER-ONLY** (`lib/post-identity.ts`): `asName`+`asIcon` post under a custom name/avatar, or `asUser` mirrors a person/bot's display name + avatar (`users.info`/`bots.info`). A non-owner (same-channel only) can't use it — wearing another member's name is the impersonation vector. The identity rides through the confirm-post gate (`PendingPost.identity`). Slack still tags a customized bot post as an app.
- **Broadcast rendering**: Slack's `markdown` block does NOT resolve control mentions (they come out plaintext), so `ThreadHandle.post` detects a `CONTROL_MENTION` token and posts that message as a `section`+`mrkdwn` block instead. The core prompt tells the model to ping with `<@id>` and broadcast with the raw `<!channel>` tokens.
- **Cross-channel posting is owner-gated** (`tools/post-message.ts`): a non-owner may only post back into the same channel kyto was mentioned in — EXCEPT a DM (`type:'user'`), which is not refused but **held for the owner's confirm click** (the ephemeral falls back to the owner's DM; the summary names the requester). **Send/edit-as-owner** (`sendAsUser`/`editAsUser`, via `SLACK_USER_TOKEN`) is only **registered** when the author is the owner, and each re-checks at execute time; `sendAsUser` can also DM a person from the owner's account (`userId`, `conversations.open` with the user token) and both accept Block Kit `blocks` (cross-channel/DM sends get `neutralizeBroadcast[Deep]` like `postMessage`).
- **Outward-facing posts need a human confirm click** (`lib/confirm-post/`, `features/confirm-post/`): a cross-channel/DM `postMessage`, and EVERY `sendAsUser`/`editAsUser`, stash the pending post (`stashPendingPost`, in-memory, 10-min TTL, single-use) and show the **owner** an ephemeral **Confirm & send / Cancel** in the current thread; the send happens only in the `confirm_post_send` action handler, which **re-checks the clicker is `OWNER_USER_ID`**. This is the anti-injection gate: a prompt injection can *request* an outward post but can't press the button. The actual send is the shared `executePostMessage`/`executeSendAsUser`/`executeEditAsUser`. Same-channel replies post immediately. A non-owner's cross-CHANNEL post is refused outright; a non-owner's DM request is the one thing that reaches the gate on their behalf — the confirm always goes to the OWNER (`ownerUserId: env.OWNER_USER_ID`), never the requester.
- **Opt-in gating** (`OPT_IN_CHANNEL`): an un-opted-in user who @s kyto gets `offerOptIn` (`lib/onboarding.ts`) — an in-thread reply with an "i accept" button. Membership of `OPT_IN_CHANNEL` is the allowlist (`lib/allowed-users.ts`).
- **`##` messages are invisible to kyto.** A message that **starts with** `##` (after stripping leading mentions) is a human-only side-channel: `isHiddenFromBot` makes `shouldIgnore` skip it AND `buildPrompt` filter it out of replayed history. Only the FIRST content line counts — a `##` later in the message (e.g. a markdown heading) does NOT hide it.
- **No channel-join greeting, ever.** The `member_joined_channel` handler posts **nothing**. Ban history: kyto once auto-joined a post-restricted channel and its greeting posted where normal members can't — it got banned. Do NOT re-add any `member_joined_channel` post. **kyto only ever speaks in reply to being invoked, never unsolicited.**
- **The bot's Slack username is a gorkie-era handle** (`gorkie__devansh_`, immutable) but its **display name is `kyto`**, so `@kyto` resolves to this bot (`U0BD3555UCQ`, app `A0BCA6D6GAV`). `auth.test`'s `user` field returns the username, not the display name. `annotateMentions` special-cases the bot's own id and annotates it as `kyto`.
- **Kyto is closed-source.** `prompts/slack.ts` says kyto's code is private with no public repo to share. It began as a private fork of the open-source gorkie — do NOT point users at `imdevarsh/gorkie-slack` as "kyto's source". A **source-available licence is now written** (`LICENSE`: readable, all rights reserved; gorkie-derived code stays MIT in `LICENSE-gorkie-MIT`), but the repo is still PRIVATE — leave that prompt line alone until it actually goes public. Pre-publication audit and the open provenance question: `docs/reference/publishing.md`.
- **Owner grounding**: `RequestHints.ownerUserId` (from `OWNER_USER_ID`) is rendered into the context block as a plain statement of who owns/built kyto, with an instruction not to hedge or invent a different origin (without it, kyto confabulated an origin and disputed the real owner's correction).

## Response style and the plan UI

- `prompts/personality.ts`: write like a human in Slack — natural sentence case, no Title Case, no ALL CAPS for emphasis, no over-punctuation; casual lowercase is fine, match the other person's register.
- **kyto MAY narrate.** In-between status updates are wanted (owner's call), and the plan splits to match.
- **The pure halves of the agent loop live in their own modules, WITH TESTS** (`lib/agent/routing.ts` fallback order, `segmentation.ts` block splitting, `carryover.ts` what a fallback model is told, `compaction-plan.ts`): the IO around them isn't testable, the decisions are, and these are the rules that broke in ways users saw. `agent/index.ts` calls into them — do NOT inline one back, a copy under test tests nothing. See TESTING.md.
- **Multi-block turns — `streamSegmented`** (`agent/index.ts`): a turn is a SEQUENCE of streamed plan messages. `renderStream` takes `emitText: true` (yields reply text as plain strings alongside task chunks, in stream order); `streamSegmented` cuts a new plan message whenever a task card arrives AFTER reply text has streamed. So `[plan] text [plan] text` — the model can post an update and keep working in a fresh block. Text is posted by `createReply` (`agent/reply.ts` — length-splitting, fence/table healing); `streamSegmented` only controls WHEN each plan opens/closes.
  - **Only VISIBLE text splits a block** (`isVisibleText` — non-whitespace). Models emit whitespace-only fragments between tool calls; `createReply` never posts those, so splitting on them opened an empty collapsible block for every stretch of tools.
  - The attempt's **Thinking card completes at first visible reply text**, so it finishes inside its own block (else a later block where its id doesn't exist leaves a perpetually spinning Thinking).
- **Reasoning** renders under `Thinking`, with a **UNIQUE task id per block**: providers reuse the same `part.id` (often `"0"`) for every step's reasoning, which collapsed all thinking into one pinned row. `renderStream` mints `reasoning-${counter++}` per `reasoning-start`, so the plan reads thinking → tool → thinking → tool.
- **Long turns rotate the stream card** (`harness.stream`, `STREAM_ROTATE_MS` = 4.5 min): Slack keeps a single `chatStream` open only ~5 min, then expires it and drops further appends — a long tool stretch would have its plan card die mid-render. So `stream()` proactively stops the current streamer and opens a fresh one (a new plan message) before the limit; task cards flow through it continuously, so the rotation lands naturally on chunk arrival.
- **A bare `skip` written as TEXT is treated as a skip** (`isBareSkipText`): a model that means to stay quiet should call the `skip` tool, but some write the word instead, and the whole "reply" then posted to the thread as a message reading `skip` followed by a usage footer. Only a reply that is NOTHING but the token counts (so "skip the first step" still posts), and it is retracted with `reply.dropTail` — not `drop()`, which would throw away a previous attempt's real answer along with it.
- **Hallucinated tool calls are hidden.** Weak models sometimes call a tool we never registered; the harness returns "Tool X not found" and the model recovers. `renderStream` is passed `knownTools` and drops any such tool-call (and its matching result/error).
- **Usage footer** (`postUsageFooter`): a muted context block showing `<output tokens> · <N> tok/s`. Per-user opt-out via `user_customizations.show_usage_footer`, toggled from App Home. The resolved model shows in the `Thinking` task, not here.

## Models / fallback

**Full detail in [`.claude/MODELS.md`](./MODELS.md) — read it before touching routing, and update it when you change routing.** Essentials:

- **Primary is pinned `qwen/qwen3.7-plus` on HackClub** (`PRIMARY_ATTEMPT`, `packages/ai/src/providers/attempts.ts`) — owner's call, 2026-07-28, replacing `moonshotai/kimi-k2.7-code`: cheaper on both sides ($0.32/$1.28 per M vs $0.73/$3.50) with ~4x the context (1M vs 262k). So **every turn spends HackClub's daily $3 cap**, and the owner's own Gemini key is the only tier behind it. 1-hour prompt caching is what keeps that affordable. The HackClub outage counter only counts failures the proxy reported (an HTTP status).
- **The HackClub 504s are a 5s header timeout in HackClub's own proxy, NOT a gateway or a provider fault** (`UPSTREAM_HEADER_TIMEOUT_MS = 5_000`, hackclub/ai `src/routes/proxy/v1/general.ts`, added 2026-05-24): it aborts any upstream request that has not returned response HEADERS in 5s and throws a 504, and something in front of it replaces that body with a Hack Club branded HTML error page, hiding the real message. This is why the failures land at a near-constant ~5.4s, why no tokens are ever billed for them, and why a plain replay of the identical request fixes ~96% of them. **Time-to-first-byte is therefore a load-bearing property of any rung** — a model that thinks before its first token loses turns at the proxy no matter how good it is.
- **The DigitalOcean tier is GONE (2026-07-27)** — it ran on an OpenRouter key with BYOK billing to a friend's DigitalOcean account, and that account stopped being provided. `digitaloceanAttempts`, `DIGITALOCEAN_MODELS`, provider `openrouter-do`, `OPENROUTER_API_KEY`/`OPENROUTER_BASE_URL` and both DO tier write-offs were deleted. Do NOT re-add a tier without a live account behind it. (A user's own OpenRouter key is a separate, still-supported BYOK provider.)
- **`LEADERBOARD_FALLBACK` is now CHEAP ON PURPOSE, not the arena top 19** (owner's call, 2026-07-27): exactly `moonshotai/kimi-k2.6` then `minimax/minimax-m3`, both verified tools-capable and both **cheaper than the pinned primary**. opus-4.8, gpt-5.6-sol, sonnet-5 and the rest of the arena list are GONE — the tier shares one $3/day cap, and falling back to a $10/M model over a transient 504 (which says nothing about the model) could spend the day's budget on one turn. Every rung must still be good enough to hand a live thread to; cheap is a constraint, not the bar. **Price any new rung before adding it** — anything materially above the primary's per-token cost belongs behind the Gemini key, not in front of it.
- **An ATTEMPT is "handled" iff IT produced reply text or a deliberate `skip`** (per-attempt, not per-turn — a continuation attempt inherits the turn's text). A model that ran tools but wrote nothing gets ONE `synthesizeFinalAnswer` nudge (same model, `tools: {}`) before falling back.
- **Fallback walks by TIER, best-first within each** (`buildFallbackQueue`): the HackClub leaderboard in rank order from opus-4.8, then the owner's Gemini key. It must NOT pivot on the primary's rank — the old "walk up from the pivot" reversed the leaderboard and fell back worst-first onto nemotron. **Every rung must be a model good enough to hand a live thread to.**
- **A gateway 504 no longer condemns the HackClub tier** (`condemnsHackclub`, `lib/agent/routing.ts`). `HACKCLUB_OUTAGE_THRESHOLD = 1` still writes the tier off on one proxy-reported failure — auth, rate limit, budget, a real 5xx — because every rung shares one proxy and one budget. A gateway status is excluded: measured 2026-07-27, the proxy 504s per REQUEST, not per model (a probe caught opus-4.8 504 while kimi-k2.7 and glm-5.2 answered fine seconds either side), so one dropped request used to skip every HackClub rung and land a live thread on `gemini-3.1-flash-lite`.
- **A model that stops answering and starts LOOPING is not "handled"** (`lib/agent/degenerate.ts`, `DegenerateOutputError`): a repetition guard trips on 8 identical consecutive lines (outside a code fence) or a runaway single line, keeps the loop out of Slack (`reply.drop()`), scrubs it from the next model's continuation context, and falls back. (nemotron once streamed "@devansh" several hundred times into a public thread and it counted as a successful turn.)
- **A model that STALLS after text has streamed still falls back.** `canContinue` covers `StreamInterruptedError`, `DegenerateOutputError`, **and `AttemptTimeoutError`** — a watchdog trip is as cut-off as a provider death, only quieter. Without the third, an 11-minute turn died on "kyto hit an error after it had already started responding" four rungs in, with fifteen healthy models still queued.
- **A model whose deployment PINS a sampling parameter needs it sent** (`REQUIRED_TOP_P`, `packages/ai/src/agent.ts`): a deployment can 400 with `top_p must be 0.95 for this model` unless that exact value is on the wire, and the SDK sends none by default — which silently killed a whole rung on every turn, visible only as a 400 partway down a fallback walk. The map is empty today (the models that needed it were DigitalOcean's); add a slug here if a provider ever rejects an omitted parameter.
- **A spent ChatGPT plan quota is PARKED, not retried** (`user_chatgpt_accounts.quota_resets_at`): a `usage_limit_reached` 429 carries `resets_at`/`resets_in_seconds`, so the account is skipped until then (clamped to a month, cleared by a completed turn) instead of prepending a doomed first attempt — plus the SDK's retries of it — to every fallback walk. A 429 is NOT an invalid login, so this is deliberately separate from `validationStatus`.
- **A provider that dies MID-STREAM does not throw** — the AI SDK turns a failed step into an `error` part and ends the stream. Text had already streamed, so the turn looked handled and went quiet mid-task. Now an error part + a last finish reason that isn't `stop` raises `StreamInterruptedError`, the ONE case where a turn that already streamed text may still fall back. The next model gets `renderContinuation` (the tail of what the user was shown) + `renderCarryover`.
- **A GATEWAY failure is replayed before it can cost a fallback** (`packages/ai/src/gateway-retry.ts`): HackClub's edge 504s in bursts (~1 request in 6 for minutes at a time, ~5.4s in, size-independent, reproducible with bare `curl`), and one dropped request per agentic step was enough to abandon a healthy primary mid-task. A response with a gateway status (408/502/503/504/520/522/524) is re-sent up to 2× (300ms/1200ms) inside the per-attempt fetch — safe because the model never ran. Every other failure, 429 and budget included, still routes away on the first try (`maxRetries` stays 1). Detail + the outage-threshold interaction in MODELS.md.
- **A tool call truncated mid-JSON is repaired** (`repairTruncatedToolCall`) — a huge `writeFile`/`postMessage` argument can hit `MAX_OUTPUT_TOKENS` mid-string.
- **Prompt caching** (1h TTL) and **`maxOutputTokens: 8000`** on the metered proxies; the latter defuses HackClub's pessimistic spend projection.
- **Gemini requires `thought_signature` replay** or every multi-step tool turn 400s.
- **Per-attempt STALL watchdog** (`ATTEMPT_TIMEOUT_MS`, default **5m**, env `AGENT_ATTEMPT_TIMEOUT_MS`): an IDLE budget re-armed on every text delta, tool call, and tool result — a long-but-working turn is NOT killed; only a genuine stall (frozen SSE, hung tool) is. It aborts ONLY the attempt signal (not the turn controller), so it's not mistaken for a user interrupt. Re-armable — the `wait` tool extends it.

### BYOK — a user's own model key

A user adds their own provider key from **App Home "Model keys"**; their turns then run on **their** key and model. Detail in `.claude/MODELS.md`. Load-bearing rules:
- **`BYOK_ENCRYPTION_KEY` (min 32 chars) gates the whole feature** (and Sign in with ChatGPT). Unset = no App Home section, no per-user routing — secrets are never stored in the clear. Stretched with scrypt into an AES-256-GCM key (`lib/byok/crypto.ts`, versioned `v1:iv:payload`). **Changing it makes every stored secret unreadable**; users re-add.
- **`packages/db` never sees a plaintext key.** `listUserModelCredentials` selects an explicit column list OMITTING the ciphertext; only `listUserModelCredentialSecrets` returns it. A key is never logged, put in a prompt/sandbox env, or in a modal's `private_metadata` — the UI shows only a stored `…tail` preview.
- **Service fallback is OFF by default, per key** (`service_fallback`). If every one of a user's keys fails and they haven't opted in, the turn ends with `ByokExhaustedError`. Opting in on ANY key unlocks the service chain for the turn.
- A key is marked **invalid only on a 401/402/403** (`recordByokOutcome`) — a 429/5xx says nothing. Marked valid whenever it completes a turn; checked with a real 1-token completion when saved (`validateCredential`).
- `generateImage` stays on the **service** provider even on a BYOK turn (a stored chat-completions key can't serve images).

### Sign in with ChatGPT (OAuth)

A user links their own ChatGPT account (Plus/Pro/Team) from **App Home** and their turns run on that subscription. Provider constants + PKCE/URL/attempt builders in `packages/ai/src/providers/chatgpt.ts` (`CHATGPT_PROVIDER = 'chatgpt-oauth'`); OAuth exchange/refresh + routing resolver in `apps/bot/src/lib/chatgpt/`; storage in `user_chatgpt_accounts` (one row per user). **Wire-level detail — the Responses API branch, the `store:false` contract, Codex headers, `MAX_OUTPUT_TOKENS` exemption — is in [`.claude/MODELS.md`](./MODELS.md); read it before touching the attempt.** Load-bearing here:

- **Gated on `BYOK_ENCRYPTION_KEY`** — the OAuth access/refresh tokens are stored encrypted with the SAME AES-256-GCM scheme as a BYOK key (an encrypted JSON blob; the public read path omits it via `getChatgptAccount`, only `getChatgptAccountSecret` returns it). `chatgptConfigured()` === `byokConfigured()`.
- **The flow is a manual code paste**, because OpenAI's Codex OAuth client (`clientId app_EMoamEEZ73f0CkXaXp7hrann`, overridable via `CHATGPT_OAUTH_CLIENT_ID`) only registers a `localhost:1455` redirect a server bot can't listen on. `startChatgptLink` mints PKCE+state (in-memory, 10-min TTL, per user); the user signs in, lands on the dead localhost callback, and pastes that URL back into the App Home modal; `completeChatgptLink` verifies state and exchanges host-side.
- **Tokens refresh before each turn** in `resolveChatgptRouting` (within 60s of expiry, at `https://auth.openai.com/oauth/token`, persisting the new blob), which then builds the attempt against `https://chatgpt.com/backend-api/codex` with a `chatgpt-account-id` header from the id_token.
- **Ordering choice (per user)**: `chatgpt_first` (default true) runs the account BEFORE kyto's shared models; false runs it only AFTER. `service_fallback` (default false) governs whether the shared chain may run at all when own-first. Both toggle from App Home. `recordChatgptOutcome` marks the login invalid ONLY on a hard 401/402/403 — a 429 is a quota, handled by the parking rule above.
- **Model choice**: the App Home picker lists exactly what the account can use — `listChatgptModels` fetches the **Codex model catalog** `GET /models?client_version=<v>` (`{models:[{slug,visibility,supported_in_api}]}`, NOT OpenAI's `/v1/models` shape), filtered to public/api-supported slugs; free-text fallback if the fetch fails. The model MUST be a real catalog slug (`gpt-5.5`, `gpt-5.6-*`); plain `gpt-5` 400s for a ChatGPT account.

### Turn logging

Every failure mode above is readable from `journalctl -u kyto.service` without a Slack transcript. Lifecycle lines in order: `[agent] turn started` → `routed turn` → `attempt started` (model, index, continuing?) → `[stream] provider error mid-stream` (status + upstream body) → `[stream] attempt stream ended` (the `StreamTally`: textChars, toolCalls, finishReasons, errors) → `attempt handled the turn` / `attempt failed, falling back` → `turn complete` / `turn failed` (durationMs, `failedAttempts` = the whole fallback walk). `streamAttempt` takes an `onError` (never remove it — without it the SDK dumps a raw unattributed stack). `errorStatus()` digs the HTTP status out of the `AI_RetryError` → `APICallError` chain; `deepErrorText()` gets the upstream body.

## Sandbox / E2B — lazy, and persistent per thread

Config in `packages/sandbox/src/config.ts`. E2B is the execution backend for the `bash`/file tools and the host tools that opt in (`browser`, `deploySite`, `getFile`, `uploadFile`).
- **Lazy** (`LazySandbox`): the real `Sandbox.create` is deferred until a tool touches it, so chat-only turns cost zero E2B.
- **Persistent per thread**: `destroy()` **pauses** rather than kills, and the thread's `sandbox_id` is remembered in `thread_sandboxes`; the next turn calls `Sandbox.connect(id)` (auto-resumes) and gets the same filesystem back (~450ms resume). This makes a **`bash` recurring reminder** useful (kyto writes/tests a script, then schedules it) and is what `wait`'s `pauseSandbox` leans on.
  - Persistence is opt-in via the injected **`SandboxStore`** (`load`/`save`/`clear`) — `packages/sandbox` stays free of a DB dependency. The bot's impl is `lib/sandbox/store.ts` (`threadSandboxStore`). A `LazySandbox` without a store is ephemeral.
  - **A thread, not a "conversation."** Every message roots its own thread, so a new top-level DM gets a **new** sandbox.
  - **Two things are fixed at CREATE time and stale on a resumed sandbox**: the `network` egress rules (which broker `GH_TOKEN`) and the create-time `envs`. Rotating `GH_TOKEN` only takes effect on a thread's next fresh sandbox. Per-command env IS re-sent on every `run()`, so the short-lived Slack proxy token stays current.
  - **A thread's sandbox is one mutable machine**; a live turn and a `bash`/`agent` reminder both reach for it. `acquireThreadSandbox`/`withThreadSandbox` serialize them (a turn holds the lock for its whole duration).
  - **A paused sandbox costs storage**, so `startSandboxReaper()` (hourly) kills anything untouched for **7 days** (`SANDBOX_TTL_MS`). `runOnce()` spins up a throwaway sandbox for callers with no thread.
- **Memory = the Slack thread.** `buildPrompt` feeds the whole thread (`slack.fetchMessages`, capped) as context; no verbatim TRANSCRIPT is persisted (the sandbox persists a *filesystem*, `langfuse` stays disabled). kyto DOES persist three kinds of DERIVED text — the `thread_thinking` reasoning cache and the `thread_summaries` compacted history (both ~30-day retention) and `memories` (until deleted); all three can paraphrase message content. The owner signed off on this explicitly AND asked Hack Club, who confirmed temporary storage is fine. Deliberate, not an oversight to revert. Full position in `docs/reference/security.md`.
- **…plus the last few turns' THINKING** (`lib/agent/thinking.ts`). Slack records only what kyto *said*; the reasoning lived in the plan's Thinking cards and was then gone, so every turn re-derived the previous turn's conclusions. `renderStream`'s `onReasoning` collects each turn's reasoning; `rememberThinking` keeps the last 3 turns per thread and `buildPrompt` injects them as `<your_previous_thinking>`. **Persisted to Postgres** (`thread_thinking`, ~30-day retention via `RETENTION_MS`, daily `startThinkingReaper`) so it survives a restart. Only the attempt that ANSWERED leaves its thinking behind, so a spiral can't seed the next turn.
- **…plus a COMPACTED digest of whatever no longer fits** (`lib/agent/compaction.ts` + `compaction-plan.ts`, `thread_summaries`). `buildPrompt` fetches up to `MAX_COMPACTION_MESSAGES` (400), replays the newest `MAX_THREAD_MESSAGES` (100) verbatim, and folds the rest into a running summary injected as `<earlier_in_this_thread>`. Past the cap the oldest messages used to just vanish, with the model never told the conversation had a beginning it couldn't see — so it contradicted decisions made earlier in the same thread. **The block ALWAYS states the count, summary or not**: a failed summarization must not silently restore the old behaviour. **Incremental** — only newly-overflowed messages are folded in, and only once `COMPACT_BATCH` (25) of them accumulate, so a long thread doesn't pay for a pass every turn (a thread's FIRST overflow is compacted immediately regardless). Runs on `subagentAttempt` (the owner's Gemini key), NOT the shared HackClub cap the turn is spending. A stored summary whose `throughMessageId` isn't in the current overflow is treated as covering nothing and redone — folding into a summary whose start we can't locate would double-count or skip a stretch. Reaped daily by `startSummaryReaper`, and deleted by the self-serve erase on the same channel-scoped terms as `thread_thinking`.

## Owner dashboard

`lib/dashboard/`, mounted on the **sites** Bun.serve at **`/_dashboard`** (so it shares `SITES_PUBLIC_HOST`; the sites name regex can't produce `_dashboard`, so no collision). Server-rendered HTML, no client framework, no external assets.

- **Gated on `DASHBOARD_PASSWORD`** (min 12 chars). Unset = the route returns null and the sites server falls through, i.e. it 404s as if never mounted.
- One password stands between the public internet and a privilege grant, so: constant-time compare, **global lockout after 8 failures** (one legitimate user, so locking globally costs nothing and there's no per-IP bookkeeping to spoof), in-memory sessions (12h), `HttpOnly; Secure; SameSite=Strict; Path=/_dashboard` cookie, and a **per-session CSRF token on every mutation**.
- Two jobs: **promote a memory to global** (read the body first — a promoted memory is prompt text on everyone's turns) and **grant/revoke GitHub trust**, including approving queued `github_requests`.
- **Approving a GitHub request grants trust and stops there** — it does NOT replay the command. That command was composed by a model in a thread that has since moved on; re-running it blind turns an approval click into an action nobody reviewed. The person asks kyto again.

## Host / deployment

- **Runs on the `oracle` server** (Oracle Linux 9, aarch64), migrated from the old `nest` server after the nest account was suspended for an AUP violation (unrelated to kyto). On oracle, Postgres is **local with no TLS**, so `packages/db/src/client.ts` uses `ssl: false` (the nest setup used `ssl: 'require'`). Keep it `false` while oracle is the deploy target.
- **`gh` is NOT in the Oracle Linux repos** (`dnf install gh` → "No match for argument: gh"); install the GitHub CLI from its official RPM repo, or authenticate git pushes with a PAT credential (see below) instead of `gh`.

## Debugging "kyto isn't responding"

- Runs under **systemd** (`kyto.service`, unit at `deploy/kyto.service`, `Restart=always`). `journalctl -u kyto.service -f -o cat`. Two unrelated Slack apps also run here (`slackbot.service`, `hackclub-ai-status-bot.service`) — different tokens, no interference.
- **Never hand-launch a second copy.** Each process opens its own Socket Mode connection and Slack delivers each event to only ONE, so a stray instance silently steals ~half the mentions. Diagnose with the `hello` frame's `num_connections` (open a throwaway socket via `apps.connections.open`) — should be **1**.
- **Slash commands work but @mentions/DMs don't = Event Subscriptions are off.** Socket Mode routes slash commands, interactivity, and events independently; if the **Enable Events** master toggle is off (it silently turned off once), `slash_commands` still deliver while events deliver nothing. Re-enable it.
- **Zombie socket**: a dropped WSS can stay TCP-`ESTAB` with a stuck send-queue (`ss -tnp | grep :443` shows non-zero Send-Q) while delivering nothing. Restart re-establishes it.
